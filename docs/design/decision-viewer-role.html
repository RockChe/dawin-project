2查證結果：現況與缺口

系統目前沒有 member 這個角色，只有兩級 super_admin / admin。 「負責人 owner」是任務上的自由文字標籤，不影響權限。

面向現況
角色roleEnum = ['super_admin','admin']，預設 admin
SessionDB-backed（每次請求 join users 撈即時 role）→ 改角色立即生效
授權層數只有兩個：safeRequireAuth()（登入即可）、safeRequireAdmin()（實為 super_admin）
寫入 action約 20 支，全部只擋「有沒有登入」——沒有「能不能寫」這一層
admin 之間無資料隔離。任何 admin 都能改彼此的任務；只有「專案本身」的改名/刪除有 owner 檢查

查證途中挖出三個既存漏洞（與 viewer 無關，但擋在路上）

A · cronBackup 是無守衛的 server action

backup.js 開頭是 'use server'，cronBackup() 是 export 且刻意不做授權 （註解寫「cron uses CRON_SECRET」）。但 CRON_SECRET 只保護 /api/backup 這條 HTTP 路徑； Next.js 會為 'use server' 檔的每一支 export 註冊可從瀏覽器呼叫的 endpoint， 而該檔又被 client 邊界的 (admin)/backup/page.jsx 引用。

後果：存在第二條不需任何憑證即可觸發整庫匯出並上傳到 R2/GDrive 的入口。

B · CRON_SECRET 沒設定時等於不設防

api/backup/route.js:14 — const expected = `Bearer ${process.env.CRON_SECRET}`。 環境變數未設定時，expected 就是字串 "Bearer undefined"， 攻擊者送同一個 header 就通過比對。全 repo 沒有任何對該變數的存在性檢查。

C · 備份憑證跟一般設定放在同一張表，讀寫只要登入

config 表同時存 owners/categories 與備份憑證。 其中 backup_r2_bucket、backup_r2_account_id、backup_gdrive_email、 backup_gdrive_folder 是明文（金鑰本身有加密）。

而 getConfig(key) 只要登入就能讀任意 key， saveConfig(key,value) 只要登入就能覆寫任意 key——包含把備份目標改指向攻擊者的 bucket。

開 viewer 這扇門之前必須先關這扇窗，否則等於是我親手把它暴露給最不受信任的帳號。

5confer 三方意見

gemini（架構視角）

  • 採納：我原本寫 role === 'viewer' 才擋，是黑名單反模式——未來第四個角色會預設可寫。改成白名單。
  • 採納：靠函式名 regex 猜哪些是寫入，是 security theater。
  • 採納：Postgres enum 加值後不可刪，回滾要整表重建。
  • 採納：dnd 給空 sensors 只廢滑鼠，抓手游標和鍵盤排序還在，要整個 bypass。
  • 反駁：說 setPassword 可能有 IDOR（改到別人密碼）——實查兩支都硬綁 session，不收 client 傳的 id。

grok（安全視角）

  • 採納：安全文件不該寫「約 20 支」，要完整 inventory。
  • 採納：靜態掃描漏了 app/api；需要負向 fixture 驗證掃描器自己會紅。
  • 採納且證實：它把「getConfig 不含密鑰」列為隱藏假設——我去查，假設不成立，就是上面的漏洞 C。這是整輪 confer 最大的收穫。
  • 採納：我說 useTaskManager 是「天然收斂點」講過頭了——它只收斂 task/subtask，專案/config/upload 都不經過。
  • 反駁：說 users.js 可被 viewer 打、能自我升級——實查全部已是 super_admin-only，且系統中根本沒有「改他人角色」的路徑。codex 覆核同意我的反駁。

目前狀態

第 3 輪剩的 2 項已照 codex 的建議補進 v4.1（新增 withRouteCap、上傳順序改成授權後才寫 R2、cron secret 改回傳布林）。 這兩處未經第 4 輪覆核（confer SOP 上限 3 輪）——都是照建議直接補，非新設計，但我不宣稱它們被驗過。

三方分歧點

雙G 與 codex 都推薦 defineAction factory（export const updateTask = defineAction(…)）。 我採納了它的實質（執行期強制），但換成 withCap callback 寫法—— 因為 'use server' 檔能不能 export 高階函式的產物，官方文件沒有明確回答 （只寫「every exported function must be async」），SWC 可能擋。 我的寫法 export 仍是字面 async function 宣告，繞開這個未知數，不需要先做 spike。

6你的裁定

題目一 · 匯出權限 → 擋掉匯出

viewer 不得使用 /api/download 與 /api/backup GET。

實作上仍做成獨立的 export capability（不硬編角色字串）， 所以日後若要放寬，只需改 permissions.js 的一行。

連帶影響測試：標 export 的入口，反向測試要斷言 viewer 失敗而非成功。

題目二 · 既存漏洞 → 跟 viewer 一起修

A（無憑證的備份 action 入口）、B（CRON_SECRET 缺失即通行）、C（任何登入者可讀寫備份憑證） 全部納入本次範圍。

7不做什麼（三方都同意排除）

  • 不做 Postgres RLS——現階段 CP 不夠。（更正我第一版寫的否決理由：grok 正確指出 user_settings 用 current_setting('app.user_id') 是可以表達的，不是技術不可行。）
  • 不用 middleware 統一擋——Next.js 的讀取與寫入 action 在網路層長得一樣 （都是帶 Next-Action header 的 POST），action id 是編譯期 hash， middleware 分不出讀寫，一律擋會連載入畫面都掛掉。
  • 不改 safeRequireAdmin 的名字——它檢查的其實是 super_admin，命名早就負債， 但改名會把 diff 擴散到一堆不相干的檔案。用 permissions.js 的語意名把意圖釘死就夠。
  • 不做「不可自我升級」防護——系統裡根本沒有「改他人角色」的功能路徑， 現在加是防一個不存在的攻擊。日後真要做改角色功能時再補。
  • 不做欄位級遮蔽——viewer 看得到 owner、notes 全部欄位。 若之後要給公司外的人用才需要，明確記錄為已知邊界。
  • 不自動降級既有帳號——現有帳號一律維持 admin，要誰變 viewer 由你指定。
