2我要更正兩件事

更正一 · 我把 /api/download 描述錯了

我在上一份決策頁裡把它寫成「匯出全量資料」。它不是。 它是開啟單一任務附件——你在任務裡點那個 ↓ 按鈕，它回傳一條 R2 的 presigned 連結讓瀏覽器去抓那一個檔案。

全 repo 只有兩個地方呼叫它：FileManagerModal.jsx:51 和 TaskModal.jsx:223， 都是使用者明確點擊的下載動作。

你是對著我那個錯誤描述回答「擋掉匯出」的。

更正二 · 「擋掉匯出」擋不住你以為它擋得住的東西

這是 codex 抓出來的，我查證屬實：viewer 一登入，全部任務資料就已經在他瀏覽器裡了。

getInitialData() 把所有 tasks / subtasks / links / files 一次送給任何登入者 （dashboard.js:21-38），存進 React state 的 allT。 而 DataTab 的 Export CSV 按鈕做的事就是 tasksToCSV(allT)——純前端，不打任何 API。

所以隱藏那兩個按鈕只是化妝。viewer 開 DevTools 就能把同一份資料倒出來。 我不能讓你以為那是一道牆。

5confer 三方意見

來源立場關鍵論點
geminiread（放行） 把單一物件讀取歸為 export 是被 URL 命名污染。「預覽比下載安全」是假象—— 沒有浮水印沙盒的話，inline 與 attachment 攻擊面相同。 拿 presigned URL 的機制缺陷去剝奪 read，是因噎廢食。
grokread（放行） 「只能看 ≠ 能下載」只在有線上預覽時才成立；你們沒有預覽路徑，擋下載＝擋閱讀檔案本體， 那不是保守，是殘缺。presigned 的外流風險 admin 也有， 差別在帳號信任度，不是端點性質變成了 export。
codex決議需修正 0.97 P1：抓出「藏按鈕只是化妝」——viewer 早已持有全量資料， 所以「單件是 read、批次是 export」在授權模型上並不自洽，只在 UI 動作名稱上成立。
P2：「舊裁定綁在錯誤前提上所以不適用」是對的， 但從「不適用」推到「使用者同意放行」是未被支持的反向推論—— 必須拿正確事實重新問你，不能自己當作已授權。

分歧點：雙G 直接給 read；codex 同意分類邏輯，但不同意我逕自套用—— 所以這頁存在。codex 這一點我完全接受：那是你的決定，不是我的。

6順帶查到的三個既有問題（不在本次範圍）

r2.js:32-34 有一條無時效的公開網址分支

如果環境變數 R2_PUBLIC_URL 有設定，getDownloadUrl 會直接回傳 ${R2_PUBLIC_URL}/${key}——沒有簽章、沒有期限。 在那種設定下所有附件是永久公開可取的，presigned 的保護根本不存在。

這跟 viewer 無關，現在就成立。要先確認你的 bucket 是不是刻意設成公開的。

  • /api/download 完全沒有 audit log——誰在什麼時候取用了哪個檔案，事後查不到。 codex 認為這比 TTL 長短更值得優先處理，我同意。
  • presigned TTL 是 900 秒（15 分鐘）。雙G 建議縮短，但 codex 說沒有足夠依據認定它必須縮， 且縮太短會讓大檔或延遲開啟失敗。依資料敏感度評估即可，不急。

7要你裁的

我的建議

/api/download（單一附件）分類為 read，viewer 可以開

理由一句：你的原話是「只能看」，附件是任務內容的一部分，擋掉它是在縮減「看」而不是擋「編輯」—— viewer 看到「請審閱附件」卻點不開，那不是唯讀，是殘缺。

雙G 立場一致，codex 也同意分類邏輯本身。

另一個選擇：分類為 export，viewer 點不開附件

如果你的考量是「viewer 會給公司外的人用，不想讓他們能產生可轉發的檔案連結」， 那這是合理的姿態——presigned URL 確實是一條可以貼給別人的連結。

代價：viewer 看得到附件清單（檔名、大小）但點不開；前端那個 ↓ 按鈕要一併隱藏。

8不做什麼

  • 不做「線上預覽 vs 下載」的區分。那要自建中繼串流 proxy，是新功能； 而且在沒有浮水印/DRM 的前提下，實質安全增益為零（雙G 一致）。
  • 不為了讓「擋掉匯出」變成真的牆而改資料載入方式。 要讓 viewer 真的拿不到全量資料，得改 getInitialData 做伺服器端範圍限縮—— 那是另一個專案級的工作，遠超出「加一個 viewer」。要做的話另開一張票。
  • 不因為前端 ↓ 會變壞按鈕就反過來決定後端分類（那是前端 task 的小成本問題）。
