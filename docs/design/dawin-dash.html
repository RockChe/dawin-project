  2. 需求二 — Projects 專案詳情頁的 Tasks 列表要能排序與篩選。 維度：狀態、日期、負責人、緊急度。設定要 per-user 持久化（「存到個人自定義的紀錄」）。
  3. 需求二的四項裁決（各附一份問答圖檔，見第 10 章）：
    · 記憶範圍＝全域一組（非每專案一組）
    · 排序四個維度、篩選三個（日期只排不篩）

    · 單一排序（非多重）＋ 三個篩選欄位全部多選

  1. 需求十 — 新增 viewer 角色。 只能看，不能做任何寫入／編輯操作。 落地為 roleEnum 第三個值 'viewer'（super_admin / admin / viewer）， 後端以 capability 制（read / self / export / write / manage） fail-closed 授權，前端依角色藏編輯 UI。細節見 full-stack/CLAUDE.md「授權層」章與第 6、9 章。
  2. 裁定一 — viewer 不得批次匯出。 export capability 涵蓋 DataTab 的兩個 Export CSV 按鈕與 /api/download；viewer 對這兩者一律看不到入口且後端 403。 誠實揭露：getInitialData() 一開始就把全量任務資料送進任何登入者的瀏覽器 （useTaskManager 的 allT state），DataTab 的 CSV 是純前端從 allT 產生。 藏按鈕擋不住 DevTools，那只是 UI policy，不是安全邊界——真正的牆是後端 withCap / withRouteCap 對每支 server action 與 API route 的授權檢查。本次沒有、也做不到「讓 viewer 的瀏覽器連資料本身都拿不到」，那是欄位級遮蔽，屬已知缺口（見 confer-final.md v4.1 §8，本次不做）。
  3. 裁定二 — 三個既存安全漏洞納入本次範圍一起修。 在盤點授權入口時發現三個既存缺陷， Rock 裁定與 viewer 角色一起修，不另開票：
    · 缺陷 A：cronBackup server action 完全沒有授權檢查（任何登入使用者都能觸發整庫備份）—— 已移除該 action，備份核心邏輯搬進 backupRunner.js，六支備份相關 action 全部改用 withCap('manage')
    · 缺陷 B：CRON_SECRET 環境變數缺失時原本 fail-open（直接放行）—— 已改為缺失／過短一律拒絕（fail-closed），比對改用 timingSafeEqual，並納入健康檢查回報
    · 缺陷 C：configTable 寫入路徑沒有 key 白名單，理論上可寫入任意 key（含備份憑證欄位）—— 已加 PUBLIC_CONFIG_KEYS 白名單，隔離備份憑證與一般設定
    三者皆已隨 viewer 角色一起修復並有對應測試覆蓋（authzCoverage.test.js 等）。

13.5　補記 2026-10-07：專案封存持久化

  • 專案封存改存資料庫：原本桌機 Projects 的 Archive 只是 useState(new Set())，切分頁或重新整理就消失。現在是專案層級、全團隊共享的屬性：projects.archived_at（nullable timestamp，Migration 0007）；新 server action archiveProject／unarchiveProject（write cap、寫 audit），useTaskManager 樂觀更新、失敗回復。 封存是刪除專案的安全替代：可還原、不動任務資料。已封存專案不出現在桌機專案主列表、桌機 Timeline、手機專案清單與手機時程；Overview／My Tasks／資料表不變。viewer 看不到封存／還原按鈕。 上線順序：先在正式庫手動執行 0007（ALTER TABLE "projects" ADD COLUMN "archived_at" timestamp;），再部署程式——新程式的 SELECT 會讀 archived_at，欄位沒先加會直接報錯。
