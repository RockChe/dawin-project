viewer 的資料庫上線

dawin-dash · 2026-09-08 · 程式碼全部完成、363 測試綠 · 只剩這一步，而它不可逆

1先講結論

不要直接跑 npm run db:migrate

不是因為 viewer 那一行有問題——那一行很安全。 是因為你會一次套用三支 migration，而其中兩支的實際狀態沒人確定。

真正不可逆的不是「加一個 enum 值」，是在一段不確定的歷史上，把三支 migration 當成一個原子操作推下去。

2查證：實際會發生什麼事

我原本以為這步是「產生一支只有一行的 migration，跑掉就好」。查證後不是。

支數內容狀態
0003 user_settings 表 ＋ FK ＋ 7 個 index（共 9 個物件） 不確定 CLAUDE.md 說正式環境未套用
0004 task_status 加「暫緩」（BEFORE '提案中'） 不確定 同上
0005 本次要的：role 加 viewer
附帶的：2 個 ADD COLUMN ＋ 5 個 CREATE INDEX		 新產生 但夾帶了既有欠帳

0005 的後七句不是這次改動引入的。source 欄位與那些 index 早就寫在 schema.js 裡了（git 追出來是「負責人彩色標籤／建立者來源追蹤」和「全站效能優化 — DB index」 那兩個 commit 加的），只是當時沒人補跑 db:generate。這次一跑就全被打包進來。

0005 的完整內容

ALTER TYPE "public"."role" ADD VALUE 'viewer';              ← 本次唯一要的
ALTER TABLE "projects" ADD COLUMN "source" varchar(50);      ← 既有欠帳
ALTER TABLE "tasks" ADD COLUMN "source" varchar(50);         ← 既有欠帳
CREATE INDEX "audit_log_action_created_at_idx" ...           ← 既有欠帳
CREATE INDEX "backup_history_status_idx" ...                 ← 既有欠帳
CREATE INDEX "backup_history_created_at_idx" ...             ← 既有欠帳
CREATE INDEX "subtasks_sort_order_idx" ...                   ← 既有欠帳
CREATE INDEX "tasks_sort_order_idx" ...                      ← 既有欠帳

全部語句都沒有 IF NOT EXISTS

如果正式環境已經有這些欄位或 index（例如有人用過 db:push—— CLAUDE.md 自己就留了「正式環境若曾 db:push 過需先核對」這句警告）， 第一句衝突就會中止整支 migration，而且部分套用後重跑會直接死在同一句。

而且文件本身不可信

CLAUDE.md 說「scripts/baseline-migrations.mjs 已就緒」——那支腳本已經不在 repo 裡了。 它說「0003/0004 production apply 尚未執行」，但既然文件在別處已被證實過期，這句也不能當真。

（同一份文件說測試有 89 個，實際是 363 個。）

3問題結構

4confer 三方意見

一個技術爭議，雙G 給了相反答案，codex 裁了

gemini：ALTER TYPE ... ADD VALUE ... BEFORE「絕對不能」在 transaction 裡跑， 所以 0004 必定失敗 rollback。

grok：PG12 起可以，限制只是「同一交易內不能使用新值」，而 0004/0005 後續語句都沒用到新值。

codex 裁決（信心 0.999）：grok 對。gemini 描述的是 PostgreSQL 11 以前的限制， PG12 起正式改為允許，BEFORE/AFTER 只是同一個語法的排序選項，沒有另行禁止。 Neon 是 PG16/17，這一項不會失敗。

來源關鍵貢獻
gemini 指出 db:push 不會寫 __drizzle_migrations，所以「journal 空」不代表「物件不存在」。 也指出 CREATE INDEX 沒帶 CONCURRENTLY 會阻斷寫入。 （它對 transaction 那題判錯，見上。）
grok 擔心 0004 改變 task_status 的 enum 排序會影響 ORDER BY status。
我實查排除了這一項——本專案狀態排序全在 JS 端用 STATUSES.indexOf() 做， 全 repo 沒有任何 DB 層的 ORDER BY status。這個風險對我們不成立。
另提出「以資料庫為準、不信文件」的盤點 SQL，以及先 migrate 再部署 writer 的順序。
codex
需修正 0.97		 抓到我盤點不足：我以為 0003 只是一個 CREATE TABLE， 實際有 9 個物件（表 ＋ FK ＋ 7 個 index）。已驗證屬實。
指出 IF NOT EXISTS 不夠：它只跳過同名物件，不驗證定義是否一致—— 同名 index 可能欄位順序不同、同名 column 可能型別不同。要比對完整定義。
反駁「絕不拆 migration」：新增一支 forward-only 修復 migration 不會讓 journal 歪， 通常才是最穩健的 drift 修法。真正的原則是「不改已被任何環境套用過的歷史」。

5要你裁的

我的建議

先做唯讀盤點，看清楚再決定怎麼跑

理由一句：現在沒有任何人——包括文件——知道正式資料庫的真實狀態， 而這一步錯了就拔不掉（Postgres 不支援 DROP VALUE，回滾要整表型別重建或 PITR）。

盤點是唯讀的、零風險的，跑完就知道是 A/B/C 哪一種狀態，才有辦法選對做法。

我可以把盤點 SQL 準備好給你貼進 Neon console，或你給我一條唯讀連線我來跑。

選項二：你確定正式環境是乾淨的，直接跑

如果你很清楚沒人用過 db:push、0003/0004 確實沒套過，那原樣 db:migrate 可以。 但請先從正式環境開一個 Neon branch 演練一次——那是免費的、兩秒的事， 而且能在真實資料上驗證，比任何推理可靠。

選項三：viewer 這步先不上，只交付程式碼

程式碼側已經全部完成且測試全綠。授權層、護欄、前端全部就緒， 而且三個既存安全漏洞已經修好了——那三個跟 enum 完全無關，不需要這支 migration 就能上線受益。

viewer 帳號等你有空處理資料庫時再開。代價：viewer 功能暫時不能用。

6不做什麼

  • 不用 db:push 救正式環境。那正是造成這團 drift 的原因。
  • 不手動拆 0005 成兩支。journal、snapshot、檔名必須一對一，手動拆會讓之後的 generate 誤判狀態、產生更難查的漂移。（若要分離，正確做法是新增一支修復 migration，不是拆舊的。）
  • 不改已經被任何環境套用過的 migration 檔。__drizzle_migrations 存的是 SQL hash， 改了會 hash 分裂。
  • 不在確認 DB 狀態前偽造 journal 紀錄。手動 insert 已套用紀錄可能永久掩蓋沒執行或只執行一半的 DDL。
  • 不為了這支 migration 引入 CONCURRENTLY。codex 判定：對小型低寫入的內部看板， 普通 CREATE INDEX 通常可接受，而且包在 transaction 裡失敗還能整體 rollback。 但上線前該用實際表大小確認，不能只憑「內部看板」四個字認定。

7不管選哪個，這幾件事都成立

  • 程式碼側完全不需要這支 migration 就能上線——沒有 viewer 帳號時， admin 與 super_admin 的行為和現在一模一樣。三個安全漏洞的修補也一樣立即生效。
  • 順序必須是先 migrate、再部署會寫入 viewer 的程式。反過來的話建立 viewer 帳號會 500。
  • 執行前先從正式環境開 Neon branch（那等於一個快照），確保 PITR 視窗還在。
  • migrate 要走 direct 連線（非 -pooler）——pooler 跑 DDL/交易語意不可靠。
